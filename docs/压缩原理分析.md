runLoop 中的 Compaction 压缩逻辑详解

一、总体流程概览

Compaction 的核心目标是：当对话 token 数接近模型上下文窗口极限时，自动将旧消息压缩为一段摘要，释放上下文空间让对话可以继续。

在 runLoop 的 while(true) 循环中，compaction 涉及三个关键位置：

1. 加载消息时过滤已压缩内容 (第1319行)
2. 处理待执行的 compaction 任务 (第1374-1383行)
3. 检测溢出并触发新的 compaction (第1386-1392行)

  ---
二、逐步拆解

第一步：加载消息并过滤已压缩部分

第1319行: let msgs = yield* MessageV2.filterCompactedEffect(sessionID)

filterCompactedEffect 从数据库按从新到旧的顺序遍历消息。当它遇到一条 已完成的压缩摘要 (assistant 消息，summary: true)，就找到该摘要对应的 user 消息上的 CompactionPart：

- 如果 tail_start_id 不存在：直接截断，更早的消息全部丢弃
- 如果 tail_start_id 存在：继续向前扫描到该 ID，保留这段"尾巴"

最后返回按时间正序排列的消息列表。效果如下图所示：

数据库中的完整消息列表（时间正序）：

│  [U1] 用户："帮我建一个登录页面"                              │  ← 已被压缩，不再加载

│  [A2] 助手："已经添加了验证逻辑..."                           │  ← 已被压缩，不再加载

│  [A3] 助手：(summary=true) "摘要：创建了登录页，加了验证..."   │  ← 压缩摘要

LLM 看到的上下文 = tail 保留段 + 摘要 + 后续新消息。

第二步：扫描未完成的 compaction 任务

// 第1324-1333行
let tasks: (MessageV2.CompactionPart | MessageV2.SubtaskPart)[] = []
for (let i = msgs.length - 1; i >= 0; i--) {
// ...
const task = msg.parts.filter((part) => part.type === "compaction" || part.type === "subtask")
if (task && !lastFinished) tasks.push(...task)
}

从最新消息往回扫描，收集 lastFinished（最后一条已完成的 assistant 消息）之后的所有 compaction 和 subtask 类型的 part。这些是"还没有被处理完"的待办任务。

  ---
第三步：处理已存在的 compaction 任务

// 第1367行
const task = tasks.pop()

// 第1374-1383行
if (task?.type === "compaction") {
const result = yield* compaction.process({
messages: msgs,
parentID: lastUser.id,
sessionID,
auto: task.auto,
overflow: task.overflow,
})
if (result === "stop") break
continue
}

如果在消息流末尾发现了一个未处理的 CompactionPart，调用 compaction.process() 来执行压缩。process 内部做这些事：

1. select() — 将消息分为 head（要压缩的旧消息）和 tail（要保留的最近几轮），保留的轮数默认2轮，token 预算为可用上下文的25%（2K~8K）
2. 调用压缩 agent — 一个只会生成文本、没有任何工具权限的 hidden agent，把 head 部分发给它生成结构化摘要
3. 保存摘要 — 作为 summary: true 的 assistant 消息存储
4. 处理 overflow 回放 — 如果是因为上下文溢出触发的（overflow: true），会将被截断的真实用户消息"回放"到压缩后的消息流中，保证用户的请求不会丢失

process 返回值：
- "stop" — 压缩失败或用户手动触发且无需继续，跳出循环
- "continue" — 压缩成功，继续下一轮循环

压缩过程示意：

压缩前的消息流（LLM 即将溢出）：
┌───────────────────────────────────────────────────┐
│  [U1] "帮我写一个 REST API"                        │ ─┐
│  [A1] "好的，我创建了路由..."  (token: 15000)       │  │
│  [U2] "加上认证中间件"                              │  ├─ head（将被压缩）
│  [A2] "已添加 JWT 认证..."    (token: 20000)       │  │
│  [U3] "写单元测试"                                 │ ─┘
│  [A3] "测试已写好..."         (token: 25000)       │ ─┐ tail（保留）
│  [U4] "部署到 staging"                             │  │
│  [A4] "已配置 Docker..."      (token: 30000) ← 溢出│ ─┘
└───────────────────────────────────────────────────┘

系统检测到 A4 的 token 超过 usable budget → 创建 compaction

压缩后的消息流：
┌───────────────────────────────────────────────────┐
│  [U3] "写单元测试"              ← tail 起点        │
│  [A3] "测试已写好..."                              │
│  [Uc] (compaction part, tail_start_id=U3)         │
│  [Ac] summary=true                                │
│       "摘要：                                      │
│        - 目标：构建 REST API 并部署                  │

└───────────────────────────────────────────────────┘

注意 overflow 回放机制：原来的 [U4] "部署到 staging" 这条消息在压缩前是导致溢出的那一轮，压缩后被"回放"为新的 [U4']，确保用户的请求不会被吞掉。

  ---
第四步：检测溢出并触发新的 compaction

// 第1386-1393行
if (
lastFinished &&
lastFinished.summary !== true &&
(yield* compaction.isOverflow({ tokens: lastFinished.tokens, model }))
) {
yield* compaction.create({ sessionID, agent: lastUser.agent, model: lastUser.model, auto: true })
continue
}

每次循环迭代中，如果：

1. 存在一条已完成的 assistant 消息 (lastFinished)
2. 该消息本身不是压缩摘要 (summary !== true，避免摘要本身又触发压缩的无限循环)
3. 该消息的 token 使用量 >= 可用上下文预算

则调用 compaction.create() 插入一条新的 compaction user 消息（auto: true），然后 continue 回到循环顶部，下一轮迭代就会走到上面"第三步"的处理逻辑。

isOverflow 的计算方式：
- 可用预算 = model.limit.input - reserved（reserved 默认 min(20000, maxOutputTokens)）
- 如果 input + output + cache.read + cache.write >= 可用预算 → 溢出

三、完整生命周期：以消息列表视角展示

下面用一个完整的对话演示整个 compaction 生命周期：

=== 初始对话（token 逐渐累积）===

循环第1轮:
msgs = [U1, A1]              token使用: 5K / 100K可用   → 正常

循环第2轮:
msgs = [U1, A1, U2, A2]     token使用: 25K / 100K可用  → 正常

循环第3轮:
msgs = [U1..A2, U3, A3]     token使用: 55K / 100K可用  → 正常

循环第4轮:
msgs = [U1..A3, U4, A4]     token使用: 85K / 100K可用  → 正常

循环第5轮:
msgs = [U1..A4, U5, A5]     token使用: 105K / 100K可用 → 溢出!


=== 触发压缩 ===

    → isOverflow() 返回 true
    → compaction.create() 插入 [Uc] (compaction part, auto=true, overflow=true)
    → continue 回到循环顶部

循环第5轮(续):
msgs = [U1, A1, U2, A2, U3, A3, U4, A4, U5, A5, Uc]
→ 检测到 Uc 是 compaction task
→ compaction.process() 开始：

      1) overflow=true, 找到最后真实用户消息 U5, 保存为 replay
         截掉 U5/A5, 待处理消息 = [U1..A4, Uc]

      2) select() 分割:
         head = [U1, A1, U2, A2, U3, A3]    (要压缩的旧消息)
         tail = [U4, A4]                     (保留最近2轮)
         tail_start_id = U4

      3) 发送 head 给压缩 agent, 生成摘要 Ac (summary=true)

      4) 回放 replay: 创建新 U5' 包含原 U5 的内容

    压缩后数据库状态:
    [...U1, A1, U2, A2, U3, A3, U4, A4, Uc, Ac(summary), U5']

    → continue 回到循环顶部


=== 压缩后继续对话 ===

循环第6轮:
filterCompactedEffect 加载:
┌─────────────────────────────────┐
│ [U4]  "部署到 staging"          │ ← tail
│ [A4]  "已配置 Docker..."        │ ← tail
│ [Uc]  (compaction part)         │
│ [Ac]  摘要: "构建了API..."      │ ← 摘要替代 U1~A3
│ [U5'] "把样式改一下"            │ ← 回放的用户消息
└─────────────────────────────────┘

    token使用: ~20K / 100K可用  → 大量空间被释放!
    → 正常调用 LLM 生成 A6

四、额外机制：Prune（裁剪）

循环结束后（第1532行），还有一个轻量级的 compaction.prune()：

yield* compaction.prune({ sessionID }).pipe(Effect.ignore, Effect.forkIn(scope))

Prune 不做完整的摘要生成，只是将旧的 tool 输出内容清空（替换为 "[Old tool result content cleared]"），释放 token 空间。保护最近 40K token 的工具输出不被裁剪，超出部分如果累计 >20K token
则执行裁剪。需要在配置中显式开启 compaction.prune: true。
